一、一句话原理
--------------------------------------------------------
大模型只负责「把用户的话整理成 JSON」，不负责说话。
所有给用户看的文字，全部来自代码返回的 render，一个字不改。
这样判定结果才是确定的，不会被模型自由发挥污染。


二、画布结构（四个节点，顺序不能反）
--------------------------------------------------------
开始(query)
  -> 大模型「信息抽取」
  -> 代码「判定」
  -> 结束(result = render)

不要省掉大模型节点。省掉的话，用户打的自由文本进不了代码，
代码收到的 facts 永远是空的，界面会一直重复同一句
「现场发现哪些问题……」，说什么都没反应。


三、开始节点
--------------------------------------------------------
参数只有 1 个：

  参数名    类型      描述
  query     String    用户本轮输入

关键：只留 query。
industry 和 facts 两个参数要删掉——对话型工作流里没人给它们填值，
留着只会让你以为接上了，实际每轮都是空的。

如果平台要求至少 2 个参数，就加一个 query2(String)，同样引用对话输入，
不要加 industry / facts。


四、大模型节点「信息抽取」
--------------------------------------------------------
输入：query（引用开始节点）；有「对话历史」变量的话一起选上
输出：1 个 String
温度：0（或最低）

系统提示词（整段复制，不要改标点）：

---------- 提示词开始 ----------
你是信息抽取器。读全部对话历史，输出一个 JSON，不要任何解释，不要向用户提问。

输出格式：
{"industry":"领域","facts":{}}

一、industry
凡涉及粉尘（木粉尘、铝镁粉尘、面粉、糖粉、饲料、家具厂、打磨抛光车间等），
一律输出 "粉尘涉爆"。
看不出来输出 ""。

二、facts 的键只能是下列 12 个，没确认的不要出现
dust_collector.type                   dry / wet / none
dust_collector.dust_kind              metal / wood / other
dust_area.layout_violation            布尔
dust_collector.mixed_shared           布尔
dust_collector.control_measures       数组，只收已装措施：vent 泄爆 / inerting 惰化 / suppression 抑爆
dust_collector.positive_pressure      布尔
dust_collector.gravity_or_tunnel_duct 布尔
dust_collector.no_ash_discharge       布尔
dust_area.electrical_not_proof        布尔
process.no_debris_removal             布尔
dust_area.no_hydrogen_or_damp_proof   布尔
dust.cleaning_not_implemented         布尔

三、布尔字段都是「隐患情形」，缺失或违规才填 true
用户说「没装 / 没有 / 不防爆 / 没落实 / 积尘严重 / 共用一套 / 拿地沟当风道」，
对应字段填 true。
用户说「装了 / 有 / 符合要求」，对应字段填 false。
用户没提到，就不要输出这个键。

四、control_measures 的专门规则
只收用户明确说「装了」的措施。
说「只装了泄爆」，就给 ["vent"]，不许补全成三种。
说「没装泄爆」，不要输出这个键，也不要给空数组 []。
只有说「一种都没装 / 什么措施都没有」，才给 []。
（这条最要紧：配的是 all_absent，给 [] 等于直接判构成。）

五、多轮累计
每次都要读全部历史，输出截至目前累计的结果，不是只输出本轮新增。
---------- 提示词结束 ----------


五、代码节点「判定」
--------------------------------------------------------
入参只有 1 个：

  参数名    类型      值（引用）        描述
  payload   String    大模型节点输出    领域与现场情况 JSON

出参 4 个（够跑通）：

  参数名      类型     描述
  verdict     String   HIT 构成 / MISS 不构成 / PENDING 待核实 / NA 全不适用
  stage       String   分支判断用：need_industry / describe / ask / hit / miss / na
  render      String   给用户看的文本，直接送结束节点
  ask_more    Integer  还剩几项要问，0 表示问完即可出结论

要接文书或跑评测，再加这几个（类型都选 String，checked 选 Integer）：

  hits        命中条款明细（含原文、处罚依据）
  pending     信息不足的条款
  na          被判定不适用的条款
  need_ask    待追问清单（字段 + 问句）
  ask_batch   本轮实际问的 2 条
  checked     实际判定了几条
  facts_used  实际用到的字段

粘贴要点（缩进相关）：
  1. 整份粘贴，从第一行 import json 到最后的 if __name__ == "__main__"。
     只粘 main 会报 NameError。
  2. 用 Ctrl+Shift+V 纯文本粘贴，别用带格式粘贴，否则缩进会被重排。
  3. 粘完看两行是否顶格：第 1 行 import json、第 830 行附近
     def main(args: dict) -> dict:。这两行顶格，其余就不会错。
  4. 文件本身已确认：0 个 Tab、块缩进只有 4/8/12/16、换行是 LF。
     若平台报 IndentationError / TabError，是编辑器把空格转成了 Tab，
     打开「插入空格」设置，或全选后 Shift+Tab 再 Tab 一次。

三条填表硬规则：
  - 参数名只能字母、数字、下划线，不能以数字开头，不能中文，不能带横杠。
  - 入参的「值」必须引用上游节点，手填不了；所以先在开始节点建 query。
  - 描述虽然标着「可选」，实际必填，写一句中文即可。


六、结束节点
--------------------------------------------------------
  参数名    类型     值（引用）
  result    String   render

只引用 render。不要在这里再加大模型输出，
否则又会出现「您好！我是基层安全生产隐患排查助手」这类自我介绍。


七、条件分支（要分场景时加，不加也能跑）
--------------------------------------------------------
按 stage 分支，不要按 verdict 分支
（describe 和 ask 的 verdict 都是 PENDING，分不开）。

  stage 等于 need_industry  -> 输出 render（问领域 / 提示暂未接入）
  stage 等于 describe       -> 输出 render（让执法人员说现场问题）
  stage 等于 ask            -> 输出 render（本轮 1~2 个追问）
  stage 等于 hit            -> 走文书节点，再输出 render
  stage 等于 miss           -> 输出 render（未发现）
  stage 等于 na             -> 输出 render（提示核对粉尘类型与除尘方式）

九、常见报错对照
--------------------------------------------------------
现象：不管说什么都重复「现场发现哪些问题……」
原因：代码节点没接到用户原话。检查入参里有没有一个代码不认识的键名
      （比如 description / query 直接当入参）。认的只有 payload / facts /
      industry / clause_ids，其余一律忽略。

现象：三个红字「参数名称只允许字母、数字、下划线」
原因：填了中文，或写了 clause-ids 这种带横杠的名字。

现象：红色「值不允许为空」
原因：入参必须引用上游输出。先建开始节点的 query，下拉里才选得到。

现象：返回「本次检查哪个领域？」，但用户明明说了粉尘
原因：大模型节点没把 industry 写出来，或 payload 没接上（接成了空字符串）。

现象：一问就判「构成」，但现场其实没查清
原因：抽取节点把「没说装了」当成了「没装」，control_measures 给了 []。
      把提示词第四条再读一遍，只收明确说「装了」的。

现象：TabError / IndentationError
原因：编辑器把 4 空格转成 Tab。见第五节粘贴要点第 4 条。


十、改完条款后怎么同步
--------------------------------------------------------
条款都在 D:\kb\dust10\DUST-10-001.json ~ 010.json。
改完按顺序跑三条命令，再重新粘贴代码：

  python D:\ict\_merge_jsonl.py

平台上的改动不会回到本地，下次重新粘贴就丢了。


十一、其他领域怎么接（现在是空的接口）
--------------------------------------------------------
代码里只有「粉尘涉爆」一个领域的条款，其余领域会走 need_industry 提示。
要接入新领域，只改两处，判定逻辑不用动：

  1. INDUSTRY_ALIAS 加映射，例如：
       "有限空间": "有限空间",
       "受限空间": "有限空间",
  2. 条款库加对应 industry 值的条款 JSON，
     重新跑 _merge_jsonl.py 和 _sync_clauses.py。

领域匹配是模糊的：句子里含「粉尘」就算粉尘涉爆，
所以「我们是做家具的木粉尘车间」这种原话也能命中。


十二、已知取舍（答辩可能被问）
--------------------------------------------------------
1. DUST-10-004 把原文两个分支（铝镁金属粉尘正压除尘 / 其他粉尘正压吹送
   未设火花探测）合并在一个布尔字段里。所以木粉尘企业也会被问到
   「铝镁等金属粉尘除尘系统用的是正压除尘方式吗」。
   要彻底分开就得拆成两个字段，会让现场多一个勾，暂时不拆。

2. DUST-10-009 补了适用条件（粉尘种类为金属），
   木粉尘车间不会再被追问铝镁粉尘储存场所。
   同理 003 限干式、006 限金属或木质粉尘，不适用就不问、也不算「未发现」。

3. 判定只有两种结论加一种待核实：构成 / 不构成 / 信息不足。
   没有「危险等级」「隐患等级」这种说法，部令里不存在分级。
