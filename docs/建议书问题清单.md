# 《方案深度设计建议书》问题清单

> 核对对象：`docs/方案深度设计建议书.docx`（编制日期 2026-11-07，1263 行）
> 核对基准：截至 2026-11-25 的**实际实现**与**平台实测结果**
> 分级：🔴 致命（答辩会被问穿 / 涉嫌造假）｜🟠 与实测冲突 ｜🟡 内部自相矛盾 ｜⚪ 方法/文档问题

## 一、🔴 致命问题（三个）

### 1. 虚构的评测数据，且写进了演示台词和答辩提纲

建议书里出现 `86 例`、`准确率 91%`、`漏判率 3.5%` 这三个数字，共 4 处：

| 位置 | 原文 |
|---|---|
| 7.1 三分钟演示脚本（2:45–3:00） | 「切评测页：**86 例、准确率 91%、漏判率 3.5%**」 |
| 7.2 预设问答 Q3 | 「我们真正报的指标是…**重大隐患判定准确率 91%**」 |
| 7.2 预设问答 Q6 | 「评测集 **86 例**来自公开处罚决定书与事故调查报告，双人标注、第三人裁决」 |
| 7.3 一页纸答辩提纲 | 「一组数据：**86 例评测、准确率 91%、漏判率 3.5%**、单次耗时降 40%」 |

**实际情况：评测集一条都没有，`eval/` 目录是空的，从未跑过任何评测。**

这是答辩最危险的一条：评委只要问一句「这 86 例在哪、能看一下吗」，当场就没有退路。
而且 7.2 Q6 还声称「双人标注、第三人裁决」——这是**编造过程**，比编造数字更严重。

**建议**：立刻把四处全部改成占位符（如 `XX 例`、`准确率 XX%`），等 `eval/run_eval.py` 真跑出数字再回填。若赛前跑不出来，就改成「已建立 N 条金标用例，正在扩充」，**说到什么程度就写到什么程度**。

### 2. 核心技术卖点「5 个 Agent 协同」，实际只落地了 1.5 个

建议书第 4 章用整章讲五个 Agent 的职责契约（识别 / 定性 / 定级 / 处置 / 文书），并在 6.1 把它当成「智能体设计」和「多 Agent 协作」两栏的答案。

**实际上平台上的工作流只有 4 个节点、1 个大模型节点：**

| 建议书声称的 Agent | 实际状态 |
|---|---|
| Agent 1 识别（Extractor） | 🟡 部分：大模型节点在做抽取，但**没有**行业先验注入、**没有**「追问最多 3 轮」的机制 |
| Agent 2 定性（Classifier） | 🔴 未接入：工作流里没有条款候选匹配环节；`clause_search` 是独立工具，没接进主链路 |
| Agent 3 定级（Grader） | ✅ 唯一完整落地的：代码节点逐条执行判定，三态输出 |
| Agent 4 处置（Advisor） | 🔴 未实现：没有裁量基准、没有企业历史、没有首违不罚 |
| Agent 5 文书（Drafter） | 🟡 部分：`render_doc` 只有 2 类模板（现场检查记录、责令限期整改指令书），建议书要求 3 类 |

**建议**：要么改成「1 个 Agent + 确定性工具链」的诚实描述（这在工程上反而更站得住），要么明确标注「本版已实现 Agent 1/3，其余为规划」。**不要让评委自己去发现落差。**

### 3. 「置信度分级」是一个不存在的东西

全文 12 处提到置信度（高/中/低三档、阈值、颜色标签），并把它列为「回应 AI 乱判谁负责的唯一正确方式」「答辩最加分的设计」。

**实际引擎输出的是三态：`HIT` / `MISS` / `PENDING`（构成 / 不构成 / 待核实），没有任何置信度分数。**

两者是不同的东西：

| | 置信度分级 | 三态判定 |
|---|---|---|
| 含义 | 结论有多可信 | 依据齐不齐 |
| 输出 | 高/中/低 + 分数 | HIT / MISS / PENDING |
| 我们实现的 | ❌ | ✅ |

**建议**：统一口径。要么改文档成「三态判定」（推荐，因为这是真实实现且有制度依据：`PENDING` 对应「信息不足→待核实」，正是设计建议书自己想要的「宁可说不知道」）；要么在引擎里真加一个置信度字段（工作量不小且没有制度依据）。

## 二、🟠 与平台实测冲突（有证据）

我们在 11-23 ~ 11-25 实测了平台，建议书的几个隐含假设不成立：

| 建议书假设 | 实测结果 | 证据 |
|---|---|---|
| 平台能把智能体发布成可调用的 API | ❌ API 渠道在渠道接口里**不存在**；调用路径为空 | `GET /channels` 只回一条 `WEB_PAGE` |
| 平台网页渠道可对外分享 | ❌ 页面能开，但运行时返回 `OBS object retrieval failed` | 实测发消息后返回该错误 |
| 应用可通过「更新版本」重新部署 | ❌ `POST /agents/{id}/versions` 返回 **404** | 控制台网络日志，4 次尝试全部 404 |
| 工具编排只需 Skill / MCP | ⚠️ 有接入方式限制：Stdio 只吃 npm 包（两个 PyPI 官方包实测失败）；HTTP 类型需公网可达 HTTPS | `docs/平台能力实测记录.md` |

另外，4.1 的六层架构**漏了平台真正的服务化层**——「托管与运行 → 智能体运行时」（用 AgentArts SDK 打包镜像到 SWR 再部署，自动生成调用链接）。建议书把平台当成「拖节点就能对外服务」的平台，实际开发态与运行态是分开的。

**建议**：在第 4 章补一节「平台能力边界」，把我们实测到的四条写进去。这不是减分项——**主动说清边界反而是专业度**。

## 三、🟡 内部自相矛盾

### 4. 法条引用三处不一致

| 位置 | 内容 |
|---|---|
| 3.2 条款 Schema 示例 | `"penalty_ref": ["安全生产法第102条"]` |
| 实际条款库（`dust_judge.py`） | `"disposal_ref": ["安全生产法-第41条", "安全生产法-第97条"]` |
| 附录「主要法规依据」 | 列出了第四十一、九十七、一百零一、一百零二条 |

同一个「重大隐患的处置依据」，三处给了三套答案。**执法场景引错法条是硬伤**，必须逐字对照部令与法条原文统一。

### 5. 术语与 Schema 不统一

| 建议书写法 | 实际实现 |
|---|---|
| `hazard_type: 缺失型 / 状态型 / 行为型`（中文） | `status / absence / behavior`（英文枚举） |
| 字段名 `除尘系统类型`、`防控措施`（中文） | `dust_collector.type`、`dust_collector.control_measures`（英文点号） |
| `conditions[]` 为平铺数组 | `conditions: {logic: "all", items: [...]}` 嵌套结构 |

照建议书写的条款 JSON **无法被现有引擎执行**。新人按文档干活会直接卡住。

### 6. 工作量与排期口径打架

- 1.3 表格：合计 **约 61 人天**，占 120 人天的 50%，结论「留了一半缓冲」。
- 同节末：又说「必须砍功能——第 5 章 P0 清单只保留 6 个功能」。
- 但 P0 这 6 个功能本身就包含语音录入、首违不罚、3 类文书——**一个都没做完**。

里程碑也不实：

| 里程碑要求 | 实际 |
|---|---|
| W1：条款结构化 Schema 定稿 + 第一类行业条款入库（50+ 条） | 实际 10 条 |
| W3：识别 + 定性两个 Agent 跑通，10 个场景出结果 | 定性 Agent 从未接入工作流 |
| W6：评测集扩到 80 例，跑第一轮全量评测 | 评测集为 0 |

**排期里完全没有「平台摸黑成本」**——而我们光摸清平台能力边界（渠道缺失、版本接口 404、OBS 报错、Stdio 只吃 npm）就花了整整两天。

### 7. 自己定了规矩又自己违反

2.5 节结尾原文：「注意标注『估算』并说明测算方法，**不要给假精度**」。

然后在 7.1 演示台词、7.3 答辩提纲里给出了 `86 例 / 91% / 3.5%` 这种精确到小数点的数字——**正是它自己警告过的假精度**。

## 四、⚪ 方法与文档问题

### 8. 多轮追问没有状态设计

4.2 Agent 1 与 4.3 编排逻辑都要求「信息不足时主动追问，最多 3 轮」。但全文没有说**多轮之间的事实怎么累积**。

实测发现：平台工作流的抽取节点**没有接对话历史变量**，输入只有本轮 `query`。也就是说第二句只说「除尘器是干式的」，第一轮的「木粉尘」就丢了，facts 不累积，多轮追问跑不通。

这是**设计缺陷不是实现缺陷**——方案层面就该定义「facts 如何跨轮累积」。

### 9. 现象词典规模注水

1.3 表格：隐患现象词典「约 200–300 个常见现象词，5 人天」。

实际 `clause_search` 里只有 **10 组关键词、约 30 个词**，且没有独立的词典文件。

### 10. 「向量为辅」没有落地

3.4 反复强调架构是「结构化为主、向量为辅」「词典优先、向量兜底」，6.2 的 `clause_search` 伪代码第 4 步也是「语义补召回」。

实际实现只有「关键词匹配 + 字面重合打分」，**没有任何向量检索**。知识库配额 0/1 GB 完全没用。

### 11. 案例库 / 相似案例不存在

P0-6 依据链要求展开到「相似案例」；4.2 Agent 2 知识源要求「案例库（少样本示例）」；6.4 评测集要求「200–500 份真实处罚决定书」。

实际：案例库为 0，依据链只到「条款原文 + 应附证据 + 处置依据」。

### 12. P0 里有两项完全没做

建议书对 P0 的定义是「8 周内必须做完的，不做就不完整」。但：

- **P0-1 语音录入**：明确决定不做（本轮已确认）
- **P0-4 首违不罚判断**：没有任何裁量基准数据，0 实现

要么把它们降级为 P1/P2，要么承认 P0 未完成。

### 13. 与《三人分工与工作流功能规划》分工口径冲突

| 文档 | 分工 |
|---|---|
| 建议书第 9 章 | A 知识工程 / B Agent 与工程 / C 评测与材料 |
| 分工书 5.x | 人工智能 / 计算机 / 市场营销 |

**两份主文档对同一个团队给了两套分工**，且工作边界不同（建议书把「评测与材料」给第三个人，分工书把评测算「联合」、材料给市场营销）。这是团队协作最该先统一的一件事。

### 14. 没有版本更新记录

文档编制于 11-07，截至 11-25 实际偏离严重（只做 1 个领域、语音没做、文书 2 类、置信度不存在、平台外部调用不可用），但文档内**没有任何变更记录或「现状 vs 规划」标注**。看文档的人会以为这些都做了。

### 15. 第 10 章对参赛基本无用

「比赛之后：这个作品能走多远」三页篇幅，对答辩没有直接帮助。有这精力不如把 §6.4 评测集和 §5.1 P0 写实。

## 五、最该先改的三件事

按「答辩风险」排序：

1. **删掉或占位化 `86 例 / 91% / 3.5%`**（含「双人标注、第三人裁决」这句编造的过程）
2. **把「5 个 Agent」和「置信度分级」改成实际做到的描述**（1 个 Agent + 3 态判定 + 确定性工具链）
3. **统一法条引用**（处置依据到底是 41/97 还是 102，逐字核对部令原文）

这三件改完，文档才「经得起问」。其余问题（词典规模、向量、案例库、P0 未完成项）属于「说多了」，可以在修订版里降级为规划。
